# 개발·승격·기록 절차

## 작업 전

- 브랜치, origin, 작업 트리와 대상 버전을 확인한다.
- 관련 `app_*`, `strategy_*`, `core_*`, `test_*`를 함께 읽는다.
- 기존 사용자 변경과 로컬 전용 파일을 별도로 식별한다.
- 동일 기능이 세 버전에 존재해도 일괄 덮어쓰지 않는다.

## 대상 선택

- 전략·UI·점수 비중·포트폴리오 원장: `QuantBotSystem_Portfolio_Beta/`
- `QuantBotSystem_Beta/`: 기존 비밀 설정·시장 DB 호환 전용, 신규 실행 변경 금지
- 버전 선택·잠금·프로세스 수명: 저장소 루트 selector
- 배포 반영: Beta 검증 후 명시적으로 승인된 파일만 `QuantBotSystem/`

## 승격

1. Beta에서 집중 테스트와 관련 전체 테스트를 통과시킨다.
2. 배포선과의 diff를 읽고 코드 파일만 선별한다.
3. 비밀 설정, 데이터, 캐시, export, 런타임 상태는 제외한다.
4. 배포 호환 래퍼와 표준 진입점이 모두 유지되는지 확인한다.
5. 변경 근거와 검증 결과를 `CHANGELOG.md`에 기록한다.

## 기록과 Git

- 전략·검증 기준·릴리스·위험의 실질 변경은 `CHANGELOG.md`에 남긴다.
- 그런 변경은 요청된 협업 범위에 회의 메모가 포함된 경우에만
  `주간회의 메모 - QuantBot`에도 짧게 반영한다.
- 일반 리팩터링, 포맷팅, 캐시 갱신, 평범한 테스트 통과는 회의 메모에
  올리지 않는다.
- 작업 관련 파일만 stage하고 명확한 작업 단위로 커밋한다.
- push와 외부 게시·메시지 전송은 명시적으로 요청된 경우에만 한다.

## 인계

변경 버전, 변경 파일, 검증 결과, 수행하지 않은 장시간 작업, 배포선 영향,
남은 위험을 구분해 보고한다.
